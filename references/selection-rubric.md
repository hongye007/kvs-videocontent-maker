# 项目选择与评分规则

## 目标

从 GitHub Trending daily、weekly 和 monthly 各前 20 个合并去重后的候选池中，挑出对开发者最有内容价值的 5-7 个项目，并保留 2 个备选。默认选 5 个；只有第 6、7 名达到质量线且能增加新的使用场景或显著内容价值时才扩容。评分负责建立一致标准，编辑判断负责核验评分是否被营销文案误导。

## 硬淘汰

出现任一条件即排除，不进入分数竞争：

- 仓库已存在于 `content/github-trending-used.json`，且用户没有明确批准重大版本回访。
- archived、disabled、明显镜像、纯 fork 或无法确认原始来源。
- README/源码/官方文档无法支持核心主张。
- 与开发者受众没有直接使用关系，或只能靠泛化 AI 话术解释价值。
- 涉及恶意代码、绕过安全、欺诈、隐私滥用或无法合理审查的高风险用途。
- 过去 180 天无有效维护，且没有能解释本次突然 Trending 的正式 Release 或公告。

## 100 分制

人工字段统一使用 0-5 分，并在评分输入中附一句依据。

| 维度 | 权重 | 5 分标准 |
| --- | ---: | --- |
| 开发者实用性 | 25 | 能直接替代或显著改善一个真实开发步骤，使用入口明确 |
| 差异性/新鲜度 | 20 | 与近期内容和本期其他项目明显不同，有意外但不猎奇 |
| 趋势质量 | 15 | 周增量、相对增长率和最近维护共同健康，不靠单一大数 |
| 证据可信度 | 15 | README、代码、License、Release、文档或演示互相印证 |
| 表达清晰度 | 15 | 50 个中文字内能说清是什么、做什么、核心亮点 |
| 受众匹配 | 5 | 对 AI 开发者、工程师或开源用户有明确价值 |
| 组合多样性 | 5 | 为当期增加新的使用场景、技术类型或视觉证据 |

趋势质量由脚本计算：先把 daily、weekly、monthly 的原始 Star 增量分别按 1、7、30.44 天折算为周速度，再计算增量分位 6 分、增量/总 Star 的相对速度分位 5 分、最近 push 新鲜度 4 分。不要直接手填。前六项形成最高 95 分的基础质量分；组合多样性在逐项入选时动态增加最多 5 分。

## 扣分

- API 或许可字段没有明确 License：`-3`，同时在内容中避免“可自由商用”。
- 关键功能依赖付费 API、闭源服务或高规格 GPU，但 README 说明不清：`-5`。
- Demo 不可访问或关键路径无法复现：`-4`。
- 核心数字仅来自项目自述且无法验证：`-3`；夸张或误导性主张：`-8`。
- 主要是现有产品的薄封装、换皮或无实质差异的聚合：`-6`。

## 组合选择

- 最低入选线 68 分。
- 同一 owner 最多 1 个，同一 category 最多 2 个。
- 新 category 加 3 分，新 language 加 2 分，只用于组合排序，不改基础质量分。
- 最终 5-7 个项目至少覆盖 3 个 category；不足时必须人工回看后续高分候选。
- 备选保留后续最高的 2 个，并写明替换哪一类风险。

## 人工复核问题

1. 这个项目解决的具体步骤是什么？
2. 最强亮点是事实还是项目自己的营销主张？
3. 限制、成本、License 或平台门槛是什么？
4. 与最近 8 期是否重复？
5. 这 5-7 个项目放在一起，是否出现至少 3 种不同的开发场景？
6. 如果隐藏 Star 数，我仍然愿意推荐它吗？

## 评分输入

`rank_candidates.py` 接收数组或 `{ "candidates": [] }`。每个候选至少包含：

```json
{
  "repo": "owner/name",
  "category": "developer-productivity",
  "language": "TypeScript",
  "stars": 12000,
  "stars_this_period": 1800,
  "period": "weekly",
  "pushed_at": "2026-09-18T00:00:00Z",
  "ratings": {
    "developer_utility": {"score": 5, "reason": "替代一个明确的手动步骤"},
    "novelty": {"score": 4, "reason": "近期栏目没有同类项目"},
    "evidence": {"score": 4, "reason": "README、源码与 Release 一致"},
    "clarity": {"score": 5, "reason": "一句话可说明用途"},
    "audience_fit": {"score": 5, "reason": "直接面向开发者"}
  },
  "flags": {
    "archived": false,
    "license_missing": false
  }
}
```

评分数字必须带 `reason`；脚本只计算数值，编辑者负责拒绝没有证据的高分。

所有未被历史账本过滤的候选还必须包含以下中文字段，供用户确认时快速判断：

```json
{
  "summary_zh": "一句话说明它是什么，不超过 36 个中文字",
  "use_case_zh": "说明具体用来完成什么任务",
  "core_highlight_zh": "说明与同类相比最值得关注的一点",
  "risk_zh": "说明许可、依赖、成熟度、平台门槛或同质化风险；没有明显风险时写无明显风险"
}
```

评分完成后运行 `scripts/build_selection_review.py`。确认表必须展示全部未做候选，不能只输出入选项目。
